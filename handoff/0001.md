# 0001 — Build & test `dram_bank_row` on phineas (RTX 3090)

Instructions for the Windows machine (phineas, EVGA RTX 3090 FTW3 Ultra V2,
GA102 `10DE:2204`, 24 GB GDDR6X, 384-bit bus). Goal: answer the milestone
question — *can the existing unmodified `dram_bank_row --pair-test` produce
useful, reproducible results on this card?*

Repo: `https://github.com/Winfred-zz/GPU-Microarch-Bench` (fork of
`peterzheng98/GPU-Microarch-Bench`, byte-identical to upstream `main`,
tree `d28172f`). Do NOT modify `dram_bank_row.cu` yet — see step 3.

---

## 1. Prerequisites (verify, record exact versions)

In a normal PowerShell:

```powershell
nvidia-smi --query-gpu=name,driver_version,memory.total --format=csv
nvcc --version
cl 2>&1 | Select-Object -First 2
```

Required:
- NVIDIA driver **>= 580** (CUDA 13.x minimum; since CUDA 13.1 the driver is
  NOT bundled with the toolkit).
- CUDA Toolkit 13.3 at `C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.3`.
- Visual Studio 2022 (MSVC 14.42). Known gotcha from the NInfer build
  (`hosts/phineas-desktop/runbooks/ninfer-setup.md`): a stray **VS 2026
  `cl.exe`** on PATH breaks CUDA builds — use the VS 2022 prompt explicitly.

Record in the results notes: driver version, `nvcc` release line, `cl` version.

## 2. Open the correct shell

Start Menu → **"x64 Native Tools Command Prompt for VS 2022"** (this sets
`cl.exe` correctly for nvcc). `cd` to the clone's `dram_bank_row` directory.

## 3. Build — expect a compile failure on CUDA 13.3

```bat
nvcc -O3 -std=c++17 -lineinfo -gencode arch=compute_80,code=sm_80 -o dram_bank_row.exe dram_bank_row.cu
```

Expected failure (this is a finding, not an accident — capture the exact text):

```
dram_bank_row.cu(819): error C2039: 'clockRate': is not a member of 'cudaDeviceProp'
dram_bank_row.cu(834): error C2039: 'clockRate': is not a member of 'cudaDeviceProp'
```

`cudaDeviceProp::clockRate` was **removed in CUDA 13.0** ("Removed Fields and
Their Replacements" → `cudaDeviceGetAttribute(cudaDevAttrClockRate)`). The
unmodified code compiles only under CUDA 12.x.

Fallback if CUDA 12.x is installed: build there unchanged to get a baseline
run of the truly unmodified tool. Otherwise: **stop, report the error text,
wait for approval of the two-line `clockRate` fix** (see step 8). Do not
patch the source on your own.

Architecture note: `sm_80` cubin runs on the 3090 (`sm_86`) via binary
compatibility (same major, ≥ minor). CUDA 13.x still supports Ampere.

## 4. Pre-run GPU state (important for reproducibility)

This card has known CUDA hangs (`LiveKernelEvent 141`) and long-standing
Afterburner underclocks (−121 MHz core / −98 MHz mem), and thermal slowdown
under LLM load. Before any run:

- **Stop NInfer and Strata** (both occupy the card; contention pollutes
  latency data).
- Keep the usual power limit in place (300–325 W stable per
  `hosts/phineas-desktop/projects/gpu-power-management/`).
- Record before/after each run:

```powershell
nvidia-smi --query-gpu=clocks.sm,clocks.mem,temperature.gpu,power.draw,power.limit,clocks_throttle_reasons.active --format=csv
```

- If HWiNFO is running, note the GDDR6X (memory junction) temperature.
- Note whether Afterburner underclocks are active — the tool converts
  cycles→ns using the *reported* SM clock, so underclocking changes ns
  values but not cycle counts.

## 5. Smoke run (fast, ~1–2 min)

```bat
dram_bank_row.exe --device 0 --pair-test --pair-range 4 --pair-stride 1024 --pair-iters 5 --csv smoke.csv --log smoke.log
```

Success looks like:
- Device line: `[0] NVIDIA GeForce RTX 3090  GDDR6  24576 MB  sm_86`
  (the tool labels the 3090 "GDDR6" — expected: `detect_mem_type()` keys on
  bus width < 1024; "GDDR6X" is never assigned).
- `SM Clock` line reflecting the (possibly underclocked) boost clock.
- Phase 1 stride table + "Phase 1 Analysis" with conflict strides.
- `=== Phase 2 (GDDR): Pair-wise Conflict Test ===` with batch dots, then a
  "Pair-test summary" (latency range, threshold, conflicts %, bank estimate).

## 6. Full runs (reproducibility protocol)

Run the default configuration **three times**:

```bat
dram_bank_row.exe --device 0 --pair-test --csv run01.csv --log run01.log
dram_bank_row.exe --device 0 --pair-test --csv run02.csv --log run02.log
dram_bank_row.exe --device 0 --pair-test --csv run03.csv --log run03.log
```

Defaults: 4096 MB buffer, Phase 1 strides 128 B–4 MB, 200k steps × 3 iters;
Phase 2 range 32 MB, stride 256 B → capped at 100 000 tests (782 batches of
128). Runtime unmeasured — expect several minutes to tens of minutes; note
actual wall time for each run.

Compare across runs:
- Phase 1: same conflict-stride set, latency range, conflict ratio.
- Phase 2: same conflict offsets (the `***` rows / `is_conflict=1` rows in
  CSV), similar lo/hi cycle range, same bank-count estimate.
Cycle counts should agree within a few percent; large run-to-run drift is
itself a finding (thermal/power throttling).

## 9. What "useful results" means for the project

For the GDDR6X cooling investigation we need from these runs:
- Stable, repeatable **conflict-offset patterns** from Phase 2 (which
  candidate offsets are same-bank as offset 0) — the raw material for
  reverse-engineering GA102 address→partition mapping.
- A baseline bank-count estimate (summary line "Same-bank frac → ~N banks").
- Evidence the single-thread pair-test is low-noise on this card (run-to-run
  agreement), since later thermal experiments will depend on latency deltas.

## 10. Safety / known risks

- Card hangs under CUDA load historically (`LiveKernelEvent 141`,
  `nvlddmkm.sys`). Keep the power limit; if a run crashes, record the exact
  run/parameters and the nvidia-smi state, and report — do not silently
  re-run until the pattern is understood.
- The benchmark allocates ~4 GB VRAM (+ ~9 MB flush buffer); fine on 24 GB,
  but only with NInfer/Strata stopped.
- Do not run while the LLM server is serving: contention changes latencies
  and raises memory temperature, confounding the baseline.
